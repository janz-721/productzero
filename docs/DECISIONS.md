# 关键决策记录

最后更新：2026-11-10

## D1：使用 Netlify，不等待 Vercel

Vercel 账号进入安全审核，项目改用 Netlify 免费部署。Vercel 审核可以继续等待，但不阻塞产品上线。

## D2：先做产品层，不重写底层模型

项目使用 OpenAI-compatible API 和现成开源框架，重点投入在：
- 假设账本
- 决策记录
- 原型设计理由
- 产品工作流

## D3：MVP 不引入登录、数据库和团队协作

先保证一个用户能完成一次完整产品推演。复杂权限和账号体系留到验证需求之后。

## D4：Brief 使用紧凑输出

Netlify 有约 30 秒的同步函数限制，Brief 使用较小输出，并把访谈问卷改为服务器本地生成，降低超时风险。

## D5：原型生成使用单次视觉调用

原本“视觉分析 + 文本生成 HTML”需要两次模型调用，容易超过 Netlify 限制。现改为一次视觉调用同时生成分析和 HTML。

## D6：免费模型优先

当前使用智谱免费模型。模型失败时按以下原则处理：
- 429/5xx 自动切换备用模型
- 超时显示中文提示
- 不因为模型失败暴露底层 HTML 错误页

## D7：当前只支持单张参考图

单图能降低复杂度和调用时长。多图属于下一阶段能力。

## D8：不复制竞品品牌和内容

参考截图只用于布局和视觉分析。最终产物必须替换品牌、文案和核心内容。

## D9：密钥不进入仓库

真实 API Key 仅保存在本地 `.env.local` 和 Netlify 环境变量中。仓库仅保留 `.env.example`。

## D10：原型采用“紧凑蓝图 + 服务端模板”

`glm-4v-flash` 最多输出 1024 tokens，直接生成完整 HTML 会被截断；`glm-4.6v-flash` 直接生成完整 HTML 又容易超过 Netlify 时间限制。

当前方案：
- 快速视觉模型只输出品牌、分类、服务、活动、流程、FAQ 和颜色等紧凑蓝图
- 服务器使用固定安全模板渲染完整 HTML
- AI 不再直接注入 HTML，避免脚本、外链图片和破图
- 代价是个性化视觉复刻精度有限，后续可通过增加模板变体提升

## D11：参考图只保留结构，旧业务文案由服务端兜底

视觉模型偶尔仍会复制参考图中的“衣物回收、手机数码、图书回收、750元”等旧业务文案。仅在提示词中禁止不够稳定，因此在服务端归一化阶段增加旧文案检测：

- 检测到参考图专属业务词时，回退到当前产品域的相机回收文案
- 服务网格、活动、流程、FAQ 和分类字段都经过同一层保护
- 模板层继续保证无脚本、无外链图片和安全的 `sandbox=""` 预览

## D12：正式线上入口使用 productzero-demo.netlify.app

2026-11-02 在 Netlify 中按顺序确认候选站点名，首选 productzero-demo.netlify.app 可用，因此将项目从随机名称切换到该正式子域。README、项目状态和下一步计划中的地址已同步更新。

## D14：访谈从固定三问改为 5 轮逐轮生成

旧版一次生成 3 个固定主题的问题，虽然覆盖目标用户、替代方案和风险，但结构像模板问卷，后续问题不会根据上一答继续深挖。

新版每次只请求下一问，并把全部历史回答传给服务器：

- 第 1 轮确认具体用户与真实场景
- 第 2 轮根据上一答追问最近一次发生了什么
- 第 3 轮确认现有替代方案及其不足
- 第 4 轮根据上一答追问频率与实际代价
- 第 5 轮确认最危险假设和低成本验证

代价是总调用次数和等待时间增加，因此每轮只生成一个短问题，并在失败时使用对应阶段的备用问题。

## D15：清理旧版截图与自动验收资产

产品视觉和访谈流程已经变化，旧版截图、验收报告、自动截图脚本与 GitHub Actions 工作流不再代表当前产品。

- 删除旧截图和验收报告，避免 README 与作品集展示过期界面
- 删除只服务于旧截图流程的脚本和工作流，减少仓库噪音
- 新版界面定稿后重新生成截图和验收资产
## D16：从通用 AI 输出升级为证据驱动产品发现

真实试用中，模型曾一次返回多个问题，Brief 也会用“不会写 PRD、不会画原型”等通用话术覆盖用户明确说过的具体卡点。为避免产品退化成普通对话 AI，本轮采用以下约束：

- 每个访谈问题必须恰好有一个问号，只能问一件事
- 有历史回答时，问题必须引用上一轮回答中的具体对象、动作、原话或数字
- 模型返回多问或未引用上一答时，先自动重试；仍失败则改用同样承接上一答的单问备用问题
- Brief 的问题定义、假设和决策记录都必须带来源轮次与原文摘录
- 服务端校验引用是否真实存在于产品想法或访谈回答；校验失败写“证据不足”
- 下一轮验证问题只从尚未验证的假设和证据缺口生成，每道问题标注对应假设
- 结果页沿用纸色、4px 卡片和 2px 控件，用分隔线和内联来源行展示证据链，不增加新的大圆角卡片
## D17：访谈扩展为 8 轮，并重做报告阅读体验

真实试用显示，5 轮无法稳定覆盖角色、动作、卡点、替代、结果、时间、频率和风险，验证问题也容易重复已知事实或退化成是非题。本轮调整：

- 基础访谈扩展为 8 轮，每轮只补一个证据维度，并禁止跨阶段抢问
- 后续验证问题改为 4–6 个开放式问题，过滤“是否、会不会、愿不愿意、继续使用吗”等是非题
- Brief 生成要求四条假设分别覆盖问题强度、现有替代、方案价值、采用意愿或风险，禁止只复述 PPT、Figma 等工具使用行为
- 证据锚点避开“最后就卡在这一步”这类空泛片段，优先选择包含具体工具、动作、结果或数字的原文
- 结果页移除固定短侧栏，改为全长阅读布局：大标题、正文 16px 起、结论与判断均衡并排、验证问题可折叠并复制
- Markdown 导出增加证据链总览、假设账本、验证地图、建议追问和访谈记录区

## D18：Product Brief 先讲普通人能听懂的话，再保留必要专业词

本轮不扩成 PRD（准备开发时使用的详细需求文档），只优化 Product Brief 的语言、访谈体验和证据展示：

- 8 轮访谈一次只问一个信息点，优先使用“谁、当时在做什么、哪一步最麻烦、现在怎么凑合解决、后来发生了什么、花了多久、过去一个月几次”等日常问法
- 保留 Product Brief、假设、证据、风险、决策、MVP、PRD 等必要专业词，但首次出现时优先用括号解释
- 能用普通话讲清楚时，不再使用“目标用户、使用场景、核心痛点、现有替代方案、证据缺口、置信度”等术语堆叠
- 8 轮访谈后增加“确认理解”步骤，原话永久保留，整理后的意思单独可编辑；只有用户逐条确认后才能生成 Brief
- Brief 的每条重要判断同时展示来源轮次、用户原话和整理后的意思；没有原话时只显示“当前证据不足”
- 将重复的“证据链总览”和“假设账本”合并成“关键判断与依据”
- 证据状态固定为“证据不足 / 有部分线索 / 有明确访谈证据 / 已验证”，风险等级单独使用“高 / 中 / 低”，不再输出百分比置信度
- Brief 生成失败时，页面和 Markdown 导出顶部都明确写“本次生成失败，以下为演示内容，不可作为正式 Brief”
- 本轮不改原型生成主线，不新增登录、数据库、多项目或团队协作，不触发 Netlify 部署

## D19：确认理解的整理内容必须按原回答顺序一一对应

测试发现确认页出现过整理内容整体错位：第 2 轮显示了第 1 轮的整理内容，后续轮次依次错位。原因是整理接口依赖模型返回的 `index` 做匹配，模型索引一旦偏移，就会把整理内容绑定到错误轮次。

修复规则：

- 服务端只按用户提交的 8 轮原回答顺序对齐整理结果，原问题与原话永远以服务端输入为准
- 模型返回的 `index` 只作辅助标记，不再作为唯一匹配依据
- 如果整理内容缺失或在同一批结果中重复，宁可回退到对应轮次原话，也不复制其他轮次内容
- 新增整理版本号；旧版本或未标记版本的数据会自动重新整理，避免浏览器继续显示历史错位结果
- 证据回归脚本增加索引偏移和重复内容用例，防止同类错位再次发生

## D20：把 3 人试用作为形成性证据，不作为产品验证结论

完成 3 名目标用户的形成性试用后，项目从“自测 demo”升级为“有真实反馈的早期产品案例”，但证据边界必须明确：

- 3/3 完成 8 轮访谈和确认理解，说明当前流程可完成
- 3/3 认可原话可追溯，支持“原话与整理内容双轨保存”的设计
- 3/3 表示会继续使用，其中 1 人明确限定为前期发散，不能写成普遍认可
- 2/3 指出文档偏长或难扫读，下一优先级不是继续加功能，而是增加一页速览或组员阅读版
- 2/3 在反证问题上卡住，后续需要示例、可选“还没想到”或更具体的追问
- P03 使用旧版并提到已移除的百分比置信度，不把该反馈算到当前版本
- 简历和案例只使用完成率、继续使用意愿、自报用时和原话反馈，不宣称效率提升、PMF 或统计显著性
